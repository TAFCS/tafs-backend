\section{Overview}
UBL's systems call TAFS to collect school fees. There are two calls, both JSON over HTTPS, both authenticated with a
service user and password in headers:
\begin{itemize}[nosep]
  \item \textbf{Bill inquiry} (\texttt{GET}) returns the student's current voucher and the exact amount to collect today.
  \item \textbf{Bill payment} (\texttt{POST}) posts a collected payment. TAFS records it as a deposit on the voucher,
        exactly as if staff had received it.
\end{itemize}
One API serves both UBL products: \textbf{TAFSCLCC} (over the counter, net banking, UBL app; the payer gives the
5-digit CC) and \textbf{TAFSCLBILL} (1Bill; a 15-digit consumer number, any bank or wallet). The consumer number alone
decides which amount is quoted.

\tafsnote{\textbf{Status on 27 November 2026.} 1Bill tested end to end on 18 November. Waiting on UBL for the
production 1Bill prefix, its egress IP addresses (for the allow-list) and OTC / net banking testing. Collections and
UBL settlement statements are reconciled under Financial Reports $\rightarrow$ UBL Collections.}

  \item Any other length, a 15-digit number with another prefix, or CC 0 returns code \texttt{01}.
  \item More than 20 digits, or anything that is not digits, is a malformed request (HTTP 400).
\end{itemize}

\section{Amounts}\label{sec:amounts}
\begin{center}
\begin{tabularx}{\textwidth}{@{}P{0.33\textwidth} L@{}}
\toprule
\textbf{Payment date (Pakistan time)} & \textbf{Amount} \\
\midrule
On or before the due date & \texttt{amount\_within\_due\_date}: unpaid fees (net of discounts) + unpaid arrear surcharges \\
After the due date, up to the validity date & \texttt{amount\_after\_due\_date}: the above + the unpaid late fee \\
After the validity date & Not payable: code \texttt{04} \\
\bottomrule
\end{tabularx}
\end{center}
For an inquiry ``today'' is the Pakistan date when the call arrives. For a payment it is the Pakistan date of
\texttt{transaction\_datetime}, so a payment taken on the due date and posted the next morning still pays the
within-due amount.

Amounts are whole rupees. \texttt{amount} may carry up to two decimals (\texttt{90053} = \texttt{90053.00}); a
fractional value never matches and gets \texttt{06}; three or more decimals is HTTP 400. The payment must equal
\texttt{amount\_payable} exactly: partial and over-payments are refused, so UBL never creates family credit.

\subsection{1Bill charge}\label{sec:onebill}
Borne by the payer and never booked as fees: the 1LINK same-day settlement fee plus the biller charge for the slab,
rounded up to whole rupees. The slab is that of the \textbf{transaction} (bill + charge), so a charge that tips the
total over a boundary takes the next slab's charge.

\section{Which Voucher Is Collected}\label{sec:latest}
\begin{itemize}[nosep]
  \item Only vouchers released to the parent, and not VOID (replaced by a newer one), are considered.
  \item The newest one that is UNPAID, OVERDUE or PARTIALLY\_PAID is collected.
  \item If none is payable, the newest one's state is returned instead: PAID \texttt{03}, WAIVED \texttt{05},
        EXPIRED or past its validity date \texttt{04}. No voucher at all is \texttt{02}.
  \item A new voucher carries every older unpaid voucher's outstanding fees onto itself and voids the older one, so
        normally there is exactly one payable voucher holding all arrears. A fee item can be on only one payable
        voucher at a time, so the same fees are never collected twice.
  \item UBL vouchers print the plain voucher serial as the voucher number (e.g.\ \texttt{12461}).
\end{itemize}

\midrule

\bottomrule
\end{tabular}

\subsection{Backend settings}
\begin{itemize}[nosep]
  \item Credentials are compared in constant time against \texttt{UBL\_SERVICE\_USER\_ID} and
        \texttt{UBL\_SERVICE\_PASSWORD}. They are issued separately and never go in a URL, a document or a ticket.
        Missing or wrong credentials: HTTP 200 with code \texttt{10}.
  \item HTTPS only (TLS 1.2 and 1.3), behind Cloudflare.
  \item \texttt{UBL\_ALLOWED\_IPS} (comma-separated IPs or CIDRs) restricts callers; unset means no restriction. An
        invalid entry refuses \textbf{every} UBL request with 503 rather than opening the API.
  \item Rate limit per caller IP: \texttt{UBL\_RATE\_LIMIT\_PER\_MINUTE}, default 600 a minute; 0 turns it off.
  \item The caller IP is Cloudflare's \texttt{cf-connecting-ip}, believed only when the connection came from a
        Cloudflare range (\texttt{UBL\_TRUSTED\_PROXY\_RANGES} overrides the list). \texttt{X-Forwarded-For} is ignored.
  \item Maintenance mode does not block these routes.
\end{itemize}

\subsection{HTTP status}\label{sec:http}
Every business outcome, including code \texttt{10}, is HTTP 200 with the outcome in \texttt{response\_code}. The
exceptions:
\begin{center}
\begin{tabularx}{\textwidth}{@{}l l L P{0.3\textwidth}@{}}
\toprule
\textbf{HTTP} & \textbf{Code} & \textbf{When} & \textbf{Body} \\
\midrule
400 & -- & Malformed: missing or invalid field, non-digit consumer number, \textbf{any field the API does not define} &
  \texttt{\{"status":400, "message":[...], "data":null\}} \\
403 & \texttt{10} & Caller IP not on the allow-list & \texttt{response\_code}, \texttt{response\_desc}, \texttt{client\_ip} \\
429 & \texttt{99} & Rate limit exceeded; \texttt{Retry-After: 60} & same \\
503 & \texttt{99} & UBL network settings invalid on the backend & same \\
\bottomrule
\end{tabularx}
\end{center}
403, 429 and 503 are answered before any student or payment data is read. Nothing is booked.

\subsection{Request body}
\begin{longtable}{@{}p{0.3\textwidth} >{\raggedright\arraybackslash}p{0.13\textwidth} >{\raggedright\arraybackslash}p{0.49\textwidth}@{}}
\toprule
\textbf{Field} & \textbf{Required} & \textbf{Meaning} \\
\midrule
\endhead
\texttt{consumer\_number} & Yes & Same value as the inquiry \\
\texttt{amount} & Yes & Amount collected; must equal \texttt{amount\_payable} \\
\texttt{channel} & CC: yes & CC: \texttt{OTC}, \texttt{APP} or \texttt{INTERNET\_BANKING}. 1Bill: omit or \texttt{ONEBILL} \\
\texttt{payment\_method} & CC: yes & How the payer paid (Section~\ref{sec:method}). 1Bill: \texttt{ONEBILL} or empty \\
\texttt{transaction\_id} & Yes & UBL's unique reference, up to 100 characters \\
\texttt{transaction\_datetime} & Yes & ISO 8601 with offset (\texttt{2026-10-05T11:00:00+05:00}), or \texttt{YYYYMMDD} / \texttt{YYYYMMDDHHmm} / \texttt{YYYYMMDDHHmmss} in Pakistan time \\
\texttt{voucher\_number} & Advised & From the inquiry. If sent and a newer voucher exists, code \texttt{07} \\
\texttt{branch\_code} & OTC & UBL branch \\
\texttt{payer\_bank\_code}, \texttt{payer\_bank\_name} & 1Bill & Bank or wallet the payer paid from \\
\texttt{instrument\_number} & Cheque / PO & Required for \texttt{CHEQUE} and \texttt{PAY\_ORDER} \\
\bottomrule
\end{longtable}
Optional fields sent as \texttt{"\{\}"}, \texttt{""} or \texttt{null} are treated as not sent.

\subsection{Duplicates, retries and timeouts}\label{sec:retries}
\begin{itemize}[nosep]
  \item Posting is idempotent on \texttt{transaction\_id}, checked before anything else. On a timeout or \texttt{99},
        resend the same request with the same id: a payment that did go through comes back \texttt{08} with its receipt
        and is never booked twice.
  \item An id stays used even after the school reverses that deposit (it is kept in \texttt{ubl\_transactions}). The
        resend still gets \texttt{08}, with the number of the deposit that was reversed.
  \item Code \texttt{09} carries the specific reason in \texttt{response\_desc}.
\end{itemize}

\subsection{What TAFS records}
\begin{itemize}[nosep]
  \item A deposit on the voucher with \texttt{payment\_method = ubl}, \texttt{reference\_number} = the transaction id,
        \texttt{deposit\_date} = \texttt{transaction\_datetime}, and remarks such as
        \texttt{UBL OTC \textperiodcentered{} CHEQUE \textperiodcentered{} instrument 00412387 \textperiodcentered{} branch 0457}.
  \item The payment clears the late fee (if overdue) and the arrear surcharges in full, and the rest goes to the fee
        heads in the voucher's order. The voucher becomes PAID and its paid receipt is generated as for any deposit.
  \item A row in \texttt{ubl\_transactions} (amount received, amount booked, 1Bill charge, channel, method), which the
        UBL Collections reconciliation matches to UBL's settlement statement.
  \item An audit log entry by actor \texttt{ubl-bank}.
\end{itemize}

\section{Changes Since Version 1.3}
The API has not changed since version 1.3 (23 November 2026). Checking that document against the code found these
gaps, now covered above:
\begin{itemize}[nosep]
  \item Any request field or query parameter the API does not define is refused with HTTP 400 (also told to UBL on
        25 November).
  \item The HTTP 400 body is \texttt{\{"status":400,"message":[...],"data":null\}}, not UBL's \texttt{response\_code}
        format; a 403 body also carries \texttt{client\_ip}.
  \item A payment's due-date and validity checks use \texttt{transaction\_datetime}, not the time it reaches TAFS.
  \item The default rate limit is 600 requests a minute per caller IP, and a bad allow-list fails closed with 503.
  \item A transaction id stays a duplicate after its deposit is reversed; the \texttt{08} reply then names a deposit
        that no longer exists.
  \item \texttt{transaction\_datetime} also accepts \texttt{YYYYMMDDHHmm} (no seconds).
  \item The inquiry still accepts, and ignores, an optional \texttt{channel} parameter.
  \item Until \texttt{UBL\_1BILL\_PREFIX} is set, 1Bill numbers use the placeholder prefix \texttt{1000000000}. UBL had
        not issued the production prefix as of 23 November 2026.
\end{itemize}
